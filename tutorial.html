Tutorial · about 60 minutes

Build a live task board with Supabase

You will create a Supabase project from scratch, write the tables and access rules in SQL, and build a small web page where each user sees only their own tasks and new tasks appear without a refresh.

0 of 9 steps doneTick each step when it works. Progress is saved in this browser only.

Before you start

You need

  • A free Supabase account (sign in at supabase.com/dashboard)
  • A code editor, for example VS Code
  • Python 3 or the VS Code Live Server extension, to serve the page locally
  • Chrome, Edge or Firefox, including a private window for the second user
  • Basic HTML and JavaScript; no SQL experience needed

You will learn

  • How a PostgreSQL schema with foreign keys and constraints protects data
  • How the browser reads and writes through the Data API with supabase-js
  • How Auth and Row Level Security keep each user's rows private
  • How Realtime pushes new rows to an open page
Stuck? The finished code is in tutorial/solution/ and on GitHub. Each step ends with a check, and there is a troubleshooting table at the end. Background for every step is in the guide.
1

Create a Supabase project

≈ 5 min
  1. Open the Supabase dashboard and create a New project.
  2. Give it a name such as task-board-tutorial, choose a region close to you (for example London or another region in Europe) and set a strong database password. You will not need the password in this tutorial, but store it in a password manager.
  3. Wait until the project is ready; this usually takes a minute or two.
Use a new project. The SQL in step 2 creates tables. Run it in a fresh project made for this tutorial, not in a project you already use.
Check. The project dashboard opens and shows your project name at the top.
2

Create the tables and the access rules

≈ 10 min

Open the SQL Editor in the left sidebar, start a new query, paste the whole script below and press Run. Then read the notes under it: they explain what each part does.

setup.sqlrun once
-- Step 2 of the Group B Supabase tutorial. Run once in a NEW project (SQL Editor).
-- Creates two tables, turns on Row Level Security and adds the access rules.
begin;

-- Shared reference data: every signed-in user can read the project names.
create table public.demo_projects (
  id   uuid primary key default gen_random_uuid(),
  name text not null unique check (char_length(btrim(name)) between 1 and 80)
);

-- Each task belongs to one project and one user.
create table public.demo_tasks (
  id         uuid primary key default gen_random_uuid(),
  project_id uuid not null references public.demo_projects(id),
  owner_id   uuid not null references auth.users(id) on delete cascade,
  title      text not null check (char_length(btrim(title)) between 1 and 120),
  created_at timestamptz not null default now()
);
create index demo_tasks_owner_idx on public.demo_tasks(owner_id);
create index demo_tasks_project_idx on public.demo_tasks(project_id);

-- Row Level Security: nothing is reachable through the API until a policy allows it.
alter table public.demo_projects enable row level security;
alter table public.demo_tasks enable row level security;

-- Grants: which operations each role may run at all. Signed-out users get nothing.
revoke all on public.demo_projects, public.demo_tasks from public, anon, authenticated;
grant usage on schema public to authenticated;
grant select on public.demo_projects to authenticated;
grant select, insert on public.demo_tasks to authenticated;

-- Policies: which rows.
create policy "Signed in users read demo projects"
  on public.demo_projects for select to authenticated
  using (true);

create policy "Users read their own demo tasks"
  on public.demo_tasks for select to authenticated
  using ((select auth.uid()) = owner_id);

create policy "Users insert their own demo tasks"
  on public.demo_tasks for insert to authenticated
  with check ((select auth.uid()) = owner_id);

insert into public.demo_projects(name)
  values ('Presentation research'), ('Tutorial preparation');

commit;
PartWhat it does
Two tablesdemo_projects holds shared project names. demo_tasks holds tasks; each one must point at a real project (project_id) and a real user in Supabase Auth (owner_id → auth.users).
Constraintsnot null, unique and check stop empty, duplicate or over-long values for every client, whatever the page does [17].
Enable RLSWith Row Level Security on, no rows are reachable through the API until a policy allows it [4].
GrantsWhich operations a role may run. Signed-in users (authenticated) may read projects and read or insert tasks. Signed-out visitors (anon) get nothing. There is no update or delete grant.
PoliciesWhich rows. using filters what a user can read; with check tests each new row. Both compare owner_id with auth.uid(), the ID of the signed-in user [18].
Seed dataTwo project names so the dropdown has something to show.
Check. The editor reports success. In the Table Editor you can see demo_projects with two rows and an empty demo_tasks.
3

Add two test users and close sign-ups

≈ 5 min
  1. Go to Authentication → Users and click Add user [16].
  2. Choose the option that creates a user with an email and password (shown as Create new user), not an email invitation. Make sure the user is confirmed; tick Auto Confirm User if your dashboard shows it. By default, users with an unconfirmed email cannot sign in [16].
  3. Create two users, for example alice@example.com and bob@example.com, each with its own password. These are test identities; do not reuse a real password.
  4. In the Authentication settings for sign-in providers, turn off Allow new users to sign up. When it is off, only existing users can sign in [15].
Why close sign-ups? Your page will contain the project URL and publishable key. That is allowed, but with sign-ups open anyone could create an account in your project. With them closed, only your two test users can sign in.
Check. Authentication → Users lists both users. Each one has a user ID (a UUID); you will use these in step 7.

Never the secret key. A key starting sb_secret_ bypasses Row Level Security and must not be in any web page [2]. If a guide tells you to copy a long key starting eyJ, it was written for the legacy keys. If you put this folder in a public Git repository, list config.js in .gitignore.

Connect and sign in

≈ 8 min

Paste this into app.js. It creates the client, signs users in and out, and reacts to the session. The four empty functions at the end are placeholders; later steps replace them.

app.js · part 1JavaScript
'use strict';
// ---------- Step 5: connect to your project ----------
const { url, key } = window.APP_CONFIG;
if (key.startsWith('sb_secret_')) throw new Error('Never put a secret key in a web page.');
// Named db, not supabase: the script tag already defines a global called supabase.
const db = window.supabase.createClient(url, key);

const $ = id => document.getElementById(id);
let user = null;      // the signed-in user, or null
let channel = null;   // the Realtime channel (step 8)

function show(message, isError = false) {
  $('status').textContent = message;
  $('status').className = isError ? 'error' : '';
}
function explain(error) {
  return [error.code, error.message, error.details, error.hint].filter(Boolean).join(' · ');
}

// ---------- Step 5: sign in and out ----------
$('loginForm').addEventListener('submit', async event => {
  event.preventDefault();
  const { error } = await db.auth.signInWithPassword({
    email: $('email').value.trim(),
    password: $('password').value
  });
  $('password').value = '';
  if (error) show(explain(error), true);
});

$('signOut').addEventListener('click', () => db.auth.signOut());

// Runs on page load, after sign-in, after sign-out and when the token is refreshed.
// Keep this callback short and synchronous; do the real work just after it.
db.auth.onAuthStateChange((_event, session) => {
  setTimeout(() => setUser(session?.user ?? null), 0);
});

async function setUser(next) {
  if (next?.id === user?.id) return;   // same user (e.g. token refresh): nothing to redraw
  user = next;
  $('loginForm').hidden = Boolean(user);
  $('appSection').hidden = !user;
  if (!user) {
    stopLive();
    $('tasks').replaceChildren();
    show('Signed out.');
    return;
  }
  $('who').textContent = `${user.email} · ID ${user.id}`;
  show('Signed in.');
  await loadProjects();
  await loadTasks();
  startLive();
}

// <placeholders> Empty for now: steps 6 and 8 replace them with real code.
async function loadProjects() {}
async function loadTasks() {}
function startLive() {}
function stopLive() {}
// </placeholders>

show('Ready. Sign in with one of your test users.');
  • createClient(url, key) makes one client for Auth, the Data API and Realtime [14]. The CDN script in index.html provides it as the global supabase, which is why our client is called db.
  • signInWithPassword sends the email and password to Supabase Auth, which returns a session with a JWT [3]. supabase-js keeps the session in the browser and attaches the token to every later request.
  • onAuthStateChange fires when the page loads (so a refresh keeps you signed in), after sign-in and sign-out, and when the token is refreshed. We only redraw when the user actually changes.
Check. Reload the page and sign in as Alice. The form disappears and you see her email and user ID. Sign out, and the form comes back. A wrong password shows an error in red.
6

Add and list tasks

≈ 10 min

Delete the placeholder lines for loadProjects and loadTasks, then add this code at the end of app.js.

app.js · part 2JavaScript
// ---------- Step 6: read the shared projects ----------
async function loadProjects() {
  const { data, error } = await db.from('demo_projects').select('id, name').order('name');
  if (error) return show(explain(error), true);
  $('project').replaceChildren(...data.map(p => new Option(p.name, p.id)));
}

// ---------- Step 6: add a task ----------
$('taskForm').addEventListener('submit', async event => {
  event.preventDefault();
  const { error } = await db.from('demo_tasks').insert({
    project_id: $('project').value,
    owner_id: user.id,
    title: $('title').value.trim()
  });
  if (error) return show(explain(error), true);
  $('title').value = '';
  show('Task saved.');
  await loadTasks();
});

// ---------- Step 6: list tasks with their project name ----------
async function loadTasks() {
  // No owner filter: Row Level Security decides which rows come back.
  const { data, error } = await db.from('demo_tasks')
    .select('id, title, created_at, demo_projects(name)')
    .order('created_at', { ascending: false });
  if (error) return show(explain(error), true);
  $('tasks').replaceChildren(...data.map(task => {
    const li = document.createElement('li');
    li.textContent = `${task.title} (${task.demo_projects?.name ?? 'no project'}) · ${task.id}`;
    return li;
  }));
  $('count').textContent = data.length;
  $('json').textContent = JSON.stringify(data, null, 2);
}
  • db.from('demo_tasks').insert({…}) becomes an HTTP request to the Data API, which PostgREST turns into SQL [5]. We send our own user ID as owner_id, and the database checks that it really is ours.
  • demo_projects(name) inside select embeds the related project in the same response. The API finds the relationship from the foreign key [6].
  • There is no "only my tasks" filter in the query. Row Level Security adds that rule inside the database.
Check. As Alice, choose a project, add a task called "Investigate foreign keys" and save. It appears in the list with its project name, and the JSON panel shows the nested demo_projects object. Add one more task; you will need a task ID in step 7.

Prove that the rules work

≈ 8 min

Add this code at the end of app.js. Each button sends a request that the database should refuse or filter.

app.js · part 3JavaScript
// ---------- Step 7: check the rules on purpose ----------
function result(text, isError = false) {
  $('result').textContent = text;
  $('result').className = isError ? 'error' : '';
}

$('badProject').addEventListener('click', async () => {
  const { error } = await db.from('demo_tasks').insert({
    project_id: '00000000-0000-0000-0000-000000000000',
    owner_id: user.id,
    title: 'Bad project test'
  });
  result(error ? `Rejected as expected (want 23503):\n${explain(error)}` : 'Unexpected: the row was saved.', !error);
});

$('readOther').addEventListener('click', async () => {
  const { data, error } = await db.from('demo_tasks')
    .select('id, title')
    .eq('id', $('otherTask').value.trim());
  if (error) return result(explain(error), true);
  result(`Rows returned: ${data.length}\n${JSON.stringify(data, null, 2)}`);
});

$('forgeOwner').addEventListener('click', async () => {
  const { error } = await db.from('demo_tasks').insert({
    project_id: $('project').value,
    owner_id: $('otherUser').value.trim(),
    title: 'Forged owner test'
  });
  result(error ? `Rejected as expected (want 42501):\n${explain(error)}` : 'Unexpected: the row was saved.', !error);
});

Now test with two users. A private window keeps its own session, so it can be signed in as a different user.

  1. In your normal window, signed in as Alice, copy one of her task IDs and her user ID (shown at the top).
  2. Click Insert with a project that does not exist. Expect 23503: a foreign key violation. This is a data-integrity rule and fails for every user.
  3. Open a private window on http://localhost:8000 and sign in as Bob. His list is empty.
  4. Paste Alice's task ID into Another user's task ID and click Try to read that task. Expect Rows returned: 0: the using policy silently filtered the row out.
  5. Paste Alice's user ID into Another user's ID and click Try to create a task for that user. Expect 42501, "new row violates row-level security policy": the with check policy rejected it.
Read the result carefully. An empty result only proves something if the task really exists and Alice can see it. A mistyped ID also returns [].
Check. You saw 23503, Rows returned: 0 and 42501, and Alice's list still shows only her own tasks.

Go live with Realtime

≈ 8 min

First let Realtime see the table. Run this in the SQL Editor [8]:

realtime.sqlrun once
-- Step 8 of the Group B Supabase tutorial: let Realtime see new rows in demo_tasks.
alter publication supabase_realtime add table public.demo_tasks;

-- Check: this should return one row.
select pubname, schemaname, tablename
from pg_publication_tables
where pubname = 'supabase_realtime' and tablename = 'demo_tasks';

Then delete the placeholder lines for startLive and stopLive and add this at the end of app.js:

app.js · part 4JavaScript
// ---------- Step 8: live updates with Realtime ----------
function startLive() {
  stopLive();
  channel = db.channel('tasks-live')
    .on('postgres_changes',
      { event: 'INSERT', schema: 'public', table: 'demo_tasks' },
      () => {
        $('events').textContent = Number($('events').textContent) + 1;
        loadTasks();                     // fresh read, filtered by RLS again
      })
    .subscribe(state => {
      $('live').textContent = state === 'SUBSCRIBED' ? '● Live' : state;
    });
}

function stopLive() {
  if (channel) db.removeChannel(channel);
  channel = null;
  $('live').textContent = 'Offline';
}
  • The channel keeps one WebSocket open and asks for INSERT events on demo_tasks.
  • Realtime checks each event against the RLS policies before delivering it, so a user only receives events for rows they may read [9].
  • The callback does not use the event's data. It runs a fresh loadTasks(), which goes through RLS again and also brings the project name.
  1. Reload, sign in as Alice and open a second normal window next to it (same browser, so also Alice). Both should say ● Live.
  2. Add a task in the left window. Without a refresh, it appears in the right window and the events counter goes up.
  3. Keep Bob's private window open too: his list and counter do not change.
Check. The second Alice window updates by itself, and Bob receives nothing. Your own window's counter also goes up, because you are allowed to see your own new row.
9

Wrap up and go further

≈ 3 min

You have built a small but complete app: PostgreSQL holds related data with constraints, the browser uses the Data API without a server of your own, Auth identifies each user, Row Level Security keeps their rows private, and Realtime pushes new rows to open pages.

Challenges

  1. Delete your own tasks. Grant delete to authenticated, add a policy for delete to authenticated using ((select auth.uid()) = owner_id), and add a button that calls db.from('demo_tasks').delete().eq('id', id). Then try deleting one of Alice's tasks as Bob.
  2. Listen to every change. Change event: 'INSERT' to event: '*'. Note that Supabase does not apply RLS to DELETE events [8]; our fresh SELECT still only shows permitted rows.
  3. Filter by project. Add a dropdown and .eq('project_id', …) to loadTasks.

Tidy up

  • Free projects pause after a week without activity; you can restore them from the dashboard [13].
  • Delete the project when you no longer need it, or keep it as a sandbox.

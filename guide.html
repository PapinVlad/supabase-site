Chapter 1

The platform: a backend built around PostgreSQL

Backend as a Service (BaaS) means a provider runs the common backend parts for you, and your app calls them over the internet. You still design the data, the access rules and the interface, but you do not build or operate the servers.

Supabase is a BaaS whose core is a full PostgreSQL database. Supabase's documentation says that everything it uses is open source, that it uses Postgres rather than a NoSQL store, and that it relies on existing standards such as pg_dump to keep data portable [1]. Each service around the database is a separate open-source project:

Chapter 2

PostgreSQL and the Data API

Relational data

PostgreSQL stores data in tables. Each row has a primary key that identifies it, and a foreign key is a column that must match a primary key in another table. Constraints are rules the database enforces on every write, whoever sends it [17].

Our example has two tables. Projects are shared reference data; tasks belong to one user and one project. Keeping projects in their own table means each name is stored once and every task points at a project that really exists.

setup.sql (excerpt)our schema
create table public.demo_projects (
  id   uuid primary key default gen_random_uuid(),
  name text not null unique check (char_length(btrim(name)) between 1 and 80)
);

create table public.demo_tasks (
  id         uuid primary key default gen_random_uuid(),
  project_id uuid not null references public.demo_projects(id),
  owner_id   uuid not null references auth.users(id) on delete cascade,
  title      text not null check (char_length(btrim(title)) between 1 and 120),
  created_at timestamptz not null default now()
);

The Data API

The Data API is PostgREST: it reads the database schema and exposes tables as REST endpoints, so the browser can query them without server code written by us [5] [20]. The supabase-js client builds those HTTP requests. Before the API can reach a table, the database roles it uses need grants on that table [14].

app.jsJavaScript
const { data, error } = await db
  .from('demo_tasks')
  .select('id, title, created_at, demo_projects(name)')
  .order('created_at', { ascending: false });
responseJSON
[{
  "id": "…",
  "title": "Investigate foreign keys",
  "created_at": "2026-10-20T14:02:11Z",
  "demo_projects": { "name": "Presentation research" }
}]

The call becomes one GET /rest/v1/demo_tasks request. Because project_id is a foreign key, the API detects the relationship and can embed the project's name in the same response [6]. Notice there is no "where owner = me" filter: which rows come back is decided by Row Level Security, covered next.

Beyond our example. The same tables can also be queried through GraphQL, which Supabase provides with its pg_graphql extension [1], and PostgreSQL extensions such as pgvector add features like similarity search.

What a broken rule looks like

Our test button inserts a task whose project_id does not exist. PostgreSQL rejects it with 23503 (foreign key violation) and saves nothing. This error is about data integrity: it happens for every user, whoever is signed in. Compare it with 42501 in the next chapter, which is about access.

Chapter 3

Auth and Row Level Security

Who you are, and what you may do

Authentication answers "who are you?". Supabase Auth checks the email and password and returns a session containing a JWT access token [3]. The token carries the user's ID (the sub claim) and a role such as authenticated, and supabase-js sends it with every request.

Authorisation answers "what may you do?". In Supabase that decision is made inside PostgreSQL. The database reads the user ID from the token as auth.uid() and applies two layers: table grants decide which operations a role may perform, then RLS policies decide which rows. PostgreSQL evaluates grants first and only then applies RLS [2].

Our policies

setup.sql (excerpt)grants and RLS
alter table public.demo_tasks enable row level security;

revoke all on public.demo_projects, public.demo_tasks from public, anon, authenticated;
grant select on public.demo_projects to authenticated;
grant select, insert on public.demo_tasks to authenticated;

create policy "Users read their own demo tasks"
  on public.demo_tasks for select to authenticated
  using ((select auth.uid()) = owner_id);

create policy "Users insert their own demo tasks"
  on public.demo_tasks for insert to authenticated
  with check ((select auth.uid()) = owner_id);
ClauseApplies toEffect when it is false
USINGExisting rows (SELECT, and the rows UPDATE or DELETE may touch)The row is silently left out
WITH CHECKNew or changed rows (INSERT, UPDATE)The statement fails with an error

Semantics from the PostgreSQL row security documentation [18]. Wrapping auth.uid() in (select …) lets PostgreSQL evaluate it once per statement instead of once per row, which Supabase recommends for performance [4].

There is no UPDATE or DELETE grant, so the page cannot edit or delete tasks at all, and signed-out visitors (the anon role) get no table access. Supabase notes that once RLS is enabled, no data is reachable through the API with a publishable key until policies allow it [4].

Keys: why the key in the page is not a leak

KeyMaps to roleRLSWhere it belongs
Publishable sb_publishable_…anon, or authenticated once signed inAppliesBrowser, mobile app, source code
Secret sb_secret_…service_roleBypassedServers only; browsers are refused with 401

Supabase documents the publishable key as safe to expose, because it only identifies the project and every request is still checked by RLS. The secret key bypasses RLS and must never reach a browser. The older anon and service_role JWT keys are the legacy versions of these two, and Supabase is deprecating them by the end of 2026 [2]. The real risk is a table without a policy, not a visible key.

Chapter 4

Realtime: changes pushed to the page

There are two ways for a page to find out that data has changed. With polling it asks the server again every few seconds, and most answers are empty. With push it keeps one WebSocket open and the server sends a message only when something happens. Supabase Realtime is the push option [7].

Realtime offers three features: Postgres Changes (database inserts, updates and deletes), Broadcast (messages between clients, such as chat) and Presence (who is online) [7]. Our example uses Postgres Changes.

Turning it on

Realtime only sees tables that are part of the supabase_realtime publication [8]:

alter publication supabase_realtime add table public.demo_tasks;
app.jssubscribe to new tasks
channel = db.channel('tasks-live')
  .on('postgres_changes',
      { event: 'INSERT', schema: 'public', table: 'demo_tasks' },
      () => loadTasks())          // read fresh, authorised data
  .subscribe();

One task, from the database to the screen

  1. Insert. Window A1 saves a task through the Data API.
  2. Stored. PostgreSQL writes the row and checks the constraints.
  3. Captured. Realtime picks up the change from the publication.
  4. Authorised. Realtime checks, for each subscriber, whether RLS lets them read that row. Records are only sent to clients allowed to read them [9].
  5. Delivered. Window A2's callback runs.
  6. Fresh read. Our callback does not trust the event; it runs a new SELECT, which goes through RLS again and also brings the project name.
  7. Rendered. The card appears. The green highlight is our own CSS; Supabase only delivered the event.

User B, signed in elsewhere, receives nothing for A's task because step 4 filters it out.

Limits worth knowing. Supabase does not apply RLS to DELETE events, because a deleted row can no longer be checked [8]. Postgres Changes authorises every event for every subscriber, so the documentation recommends Broadcast once more than about 3,000 clients listen to the same changes [8]. Our example only listens for INSERT; edits and deletes need a manual refresh. That is a limit of our example, not of Supabase.

Chapter 5

When to use Supabase

A scenario where it fits

A student society wants a small web app: members sign in, post events, sign up for them and see the numbers change live. Three volunteers will build it in a few weeks, and nobody wants to run a server.

Supabase covers sign-in, the database, the API and live updates out of the box. The volunteers write the HTML and JavaScript, design two or three tables and write policies such as "members can only cancel their own sign-up". The free plan is enough to start.

What it saved us, and what we still built

Supabase provided

  • Hosted PostgreSQL
  • Auth with JWT sessions
  • The REST Data API
  • The Realtime server

We still built

  • The schema and constraints
  • Grants and RLS policies
  • The HTML and JavaScript frontend
  • Tests of the access rules

Firebase's main database, Firestore, stores documents in collections [24] and controls access with Security Rules [25]; its emulators are for local testing, not a self-hosted Firebase [26]. Firebase also offers PostgreSQL through SQL Connect, formerly Data Connect, generally available since April 2025 and renamed in April 2026 [21] [22] [23]. Supabase's lock-in is low to medium: the data is ordinary PostgreSQL that can be exported with pg_dump [1], but code that uses auth.users, auth.uid() and supabase-js would need rework elsewhere. Self-hosting moves security, HTTPS, email and updates back to your own team [11].

Pros and cons

Strengths

  • A real relational database with SQL, joins and constraints
  • Access rules live next to the data and apply to every client
  • Auth, API and live updates without writing a server
  • Open source, so self-hosting and data export are possible
  • A usable free tier for learning and prototypes

Weaknesses

  • You must be comfortable with SQL and policies; a missing policy is a security hole
  • Heavy custom server logic moves into Edge Functions or another service
  • Free projects pause after a week idle
  • Cost depends on usage, so it is harder to predict at scale
  • Realtime at large scale needs design choices such as Broadcast
Our verdict. Supabase is a strong fit for data-centred web apps that need sign-in, CRUD and live updates, especially prototypes and small teams, as long as the team owns its SQL and RLS. It is a weaker fit for apps dominated by custom server logic, for teams that need full control of their infrastructure, or for teams new to SQL.
